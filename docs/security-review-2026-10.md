# Security review – October 2026

Scope: the whole server (`server/`, 863 routes: 153 public, 65 user, 89 admin, 556 sub-account), the public
pages, the MCP endpoint, the mobile API, the Docker setup and dependencies – before the open-source release.
Method: automated harnesses that enumerate the router (tenant isolation, stored XSS, secret leaks) plus manual
review of authentication, CSRF, SSRF, file handling, secrets, webhooks, DoS and supply chain.
Design and protections: [security.md](security.md).

## Checked without findings

- SQL: all queries parameterised; identifiers interpolated only from code or validated keys (`KEY_RE`, allow-lists).
- XSS: 5,000+ public page renders over 27 page types with a stored payload – all escaped; funnel/blog pages
  are sandboxed (`CSP: sandbox`, no `allow-same-origin`); admin previews of owner HTML run in sandboxed iframes.
- Webhooks: Stripe (5-minute tolerance), Twilio, Meta (unsigned refused), Todoist, OpenShorts, inbound HMAC –
  all verified with constant-time comparison.
- Portals: magic links (32 bytes, 30 minutes, single use), `Origin` check plus per-session form token, strict CSP,
  `X-Frame-Options: DENY`; `next`/`back` parameters restricted to portal paths.
- MCP: every tool goes through the REST API with the caller's key (same rights, guards and audit); the
  isolation harness found no tool returning another sub-account's data.
- Mobile tokens: only `/api/mobile/*`, own rate limit, revoked with password changes.
- CORS, session cookie flags, invite links, `cspExtra` (only code-defined https/wss origins).
- File serving: uploads, form files, community images, lesson downloads, backups and academy docs resolve
  names through the database or strict patterns.

### Checked without findings (this round)

- Stripe (`/hooks/stripe`, `/hooks/stripe-agency`): constant-time HMAC, 5-minute tolerance, event ids de-duplicated before handling, every handler scopes by the location of the event; Checkout amounts always from the product row (forms with a payment field, quotes, invoices).
- Quote page `/q/<token>`: 24 random bytes, the selection is validated against the stored document, amounts are recomputed on the server, acceptance is claimed with a single `UPDATE … WHERE status IN ('sent','viewed')`.
- Consent: double-opt-in links (HMAC, expiry in the token and the row, a button instead of a GET), preference centre token per contact, redirect only to the sub-account's own setting.
- Tracking: `/t/c/<id>` redirects only to links the server wrote itself, trigger-link signatures cannot be extended (truncated HMAC), the pixel validates nothing it does not store.
- Hosted course video: signed token bound to video, member and sub-account **and** the member's session **and** a running enrolment, same-origin only, HLS names from a strict pattern, ffmpeg arguments built from server-made paths.
- `/uploads-opt/<w>/<file>`: widths from a fixed list, file names through the uploads table, at most two conversions at a time, one cached copy per width and format.
