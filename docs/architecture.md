# Aufbau

```
server/
  core/        HTTP-Router, Auth, DB (node:sqlite), Event-Bus, Templates, Zeitzonen, öffentliche Seiten
  services/    Fachlogik, die mehrere Module teilen: Kontakte, Versand (E-Mail/SMS), Opportunities,
               Workflow-Engine, Bewertungen, GHL-Import
  modules/     Ein Modul je Bereich: eigene Tabellen (migrations) + Routen (register)
  modules/index.ts   Registry – neue Module hier eintragen
  assets/forms/ Browser-Skripte und -Styles der öffentlichen Formulare (Teile, die `npm run build` minimiert; docs/forms.md)
web/src/       React-Oberfläche (eine Datei je Bereich unter pages/)
tests/         Unit- und End-to-End-API-Tests (vitest)
```

## Ein Modul hinzufügen

```ts
// server/modules/memberships.ts
import type { Module } from '../core/app.js';

export const membershipsModule: Module = {
  name: 'memberships',
  migrations: [['001-init', `CREATE TABLE courses (id TEXT PRIMARY KEY, location_id TEXT NOT NULL REFERENCES locations(id) ON DELETE CASCADE, …)`]],
  register(app) {
    app.router.get('/api/courses', 'location', (ctx) => app.db.all('SELECT * FROM courses WHERE location_id = ?', ctx.locationId));
    app.events.on('invoice.paid', (e) => { /* Zugang freischalten */ });
  },
};
```

…und in `server/modules/index.ts` eintragen. Migrationsnamen nie ändern, nur neue anhängen.

## Regeln

- **Auth je Route:** `public`, `user` (angemeldet), `admin`, `location` (angemeldet *oder* API-Schlüssel + Sub-Account). Alles mit `location` filtert auf `ctx.locationId`.
- **CSRF:** Schreibende Anfragen mit Cookie brauchen den Header `x-pghl: 1` (macht die Oberfläche automatisch).
- **Ereignisse** (`app.events.emit(locationId, type, data)`) laufen nach der Antwort; Workflows und Webhooks hängen daran. `data.contactId` startet Workflows für diesen Kontakt.
- **Rechte:** `app.guards` laufen nach der Anmeldung; das Agentur-Modul prüft dort die Bereiche eingeschränkter Logins (`server/core/permissions.ts` ordnet Routen Bereichen zu). Neue Module tragen ihre Routen dort ein – dieselbe Zuordnung nutzt der SaaS-Guard (`saas-gate.ts`), um Bereiche außerhalb des Tarifs zu sperren und Limits beim Anlegen zu prüfen.
- **Sprache der Oberfläche:** Texte bleiben deutsch im Code und laufen über `t()` aus `web/src/i18n` (`const t = useT('bereich')`, der deutsche Text ist die Nachrichten-ID); die englischen Übersetzungen liegen je Bereich in `web/src/i18n/en/*.ts`. Bereiche mit `complete: true` in `web/src/i18n/registry.ts` hält `npm run i18n:check` vollständig. Die Sprache je Person speichert `modules/language.ts` (`users.lang`, `/api/me/language`) – Anleitung: [translating.md](translating.md) (Englisch).
- **Performance:** keine Abfrage pro Sub-Account/Zeile in einer Anfrage (gruppieren, siehe `services/location-stats.ts`), Index in der eigenen Migration für jedes neue `WHERE`/`ORDER BY` auf großen Tabellen, lesende Listen/Auswertungen über `cached()` (`core/cache.ts`) bzw. `app.db.memo`, Hintergrund-Aufgaben in Scheiben von höchstens ~50 ms (`sliceTimer`), neue Seiten mit `lazyPages` – die Regeln mit Beispielen: [docs/performance.md](performance.md#rules-for-modules). `app.perf` (Ereignisschleife, langsame Anfragen/Abfragen, Job-Zeiten) → `GET /api/admin/metrics`.

## Berichte: eigene Datenquellen

Berichte & Dashboards (`modules/reports.ts`, Engine in `services/report-engine.ts`, eingebaute Quellen in `services/report-sources.ts`) lesen alles über die Liste `app.services.reportSources`. Ein Modul meldet seine Tabelle mit wenigen Zeilen an – egal, ob es vor oder nach dem Berichte-Modul registriert wird:

```ts
import type { ReportSource } from '../services/report-engine.js';
import { contactJoin, lookupTable } from '../services/report-sources.js';

const ticketContact = contactJoin('t.contact_id'); // optional: Kontaktfelder als „Kontakt: …“
const TICKETS: ReportSource = {
  key: 'tickets', label: 'Tickets', area: 'conversations',          // Recht, das Kunden-Logins brauchen (+ SaaS-Tarif)
  from: 'tickets t', location: 't.location_id', dateField: 'created_at',
  requires: ['tickets'], countLabel: 'Anzahl Tickets', joins: ticketContact.joins,
  fields: [
    { key: 'created_at', label: 'Erstellt am', type: 'date', sql: 't.created_at' },
    { key: 'status', label: 'Status', type: 'enum', sql: 't.status', options: { open: 'Offen', closed: 'Geschlossen' } },
    { key: 'agent', label: 'Bearbeiter', type: 'string', sql: 't.assigned_to', lookup: lookupTable('users', 'name'), empty: 'Nicht zugewiesen' },
    { key: 'hours', label: 'Lösungszeit', type: 'number', sql: '(julianday(t.closed_at) - julianday(t.created_at)) * 24', format: 'number' },
    ...ticketContact.fields,
  ],
  calcs: [{ key: 'close_rate', label: 'Lösungsquote', sql: `100.0 * SUM(t.status = 'closed') / NULLIF(COUNT(*), 0)`, format: 'percent' }],
};
app.services.reportSources = [...(app.services.reportSources ?? []), TICKETS];
```

- `sql`, `from`, `joins` und `calcs` sind fester Code – Nutzerwerte kommen nur als Parameter in die Abfrage; die Engine hängt den Sub-Account-Filter (`location IN (…)`), Zeitraum, Filter, `LIMIT` und eine Zeitgrenze selbst an.
- Feldtypen: `string`, `enum` (mit `options`), `number` (`format`: number, money – in Euro –, percent, days, minutes), `date` (ISO-Zeitstempel; Gruppierung nach Tag … Stunde in der Zeitzone des Sub-Accounts), `boolean` (SQL liefert 1/0), `tags` (JSON-Array). `lookup` übersetzt IDs in Namen (und Reihenfolge, z. B. Pipeline-Phasen); `noGroup` für Freitext.
- Jede Quelle bekommt automatisch die Gruppe *Sub-Account*; Quellen mit fehlenden Tabellen (`requires`) werden ausgeblendet. Ein Test, der alle Felder kompiliert, steht in `tests/reports.test.ts`.
