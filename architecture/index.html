Structure

Adding a module

Section titled “Adding a module”

…and register it in server/modules/index.ts. Never change migration names, only append new ones.

Rules

Section titled “Rules”

  • Auth per route: public, user (signed in), admin, location (signed in or API key + sub-account). Everything with location filters on ctx.locationId.

  • CSRF: Writing requests with a cookie need the header x-pghl: 1 (the UI does this automatically).

  • Events (app.events.emit(locationId, type, data)) run after the response; workflows and webhooks hook into them. data.contactId starts workflows for that contact.

  • Permissions: app.guards run after sign-in; the agency module checks the areas of restricted logins there (server/core/permissions.ts maps routes to areas). New modules register their routes there – the SaaS guard (saas-gate.ts) uses the same mapping to block areas outside the plan and to check limits on creation.

  • UI language: Texts stay German in the code and go through t() from web/src/i18n (const t = useT('bereich'), the German text is the message ID); the English translations live per area in web/src/i18n/en/*.ts. npm run i18n:check keeps areas with complete: true in web/src/i18n/registry.ts complete. Each person’s language is stored by modules/language.ts (users.lang, /api/me/language) – guide: translating.md (English).

  • Performance: no query per sub-account/row within a request (group instead, see services/location-stats.ts), an index in the module’s own migration for every new WHERE/ORDER BY on large tables, read-only lists/reports through cached() (core/cache.ts) or app.db.memo, background jobs in slices of at most ~50 ms (sliceTimer), new pages with lazyPages – the rules with examples: docs/performance.md. app.perf (event loop, slow requests/queries, job times) → GET /api/admin/metrics.

  • Background jobs via app.onTick(fn) (workflow waits, reminders, scheduled campaigns, subscription invoices, iCal sync, date triggers, backups).

Reports: custom data sources

Section titled “Reports: custom data sources”

Reports & dashboards (modules/reports.ts, engine in services/report-engine.ts, built-in sources in services/report-sources.ts) read everything through the list app.services.reportSources. A module registers its table with a few lines – no matter whether it is registered before or after the reports module:

  • sql, from, joins and calcs are fixed code – user values enter the query only as parameters; the engine itself appends the sub-account filter (location IN (…)), the period, filters, LIMIT and a time limit.
  • Field types: string, enum (with options), number (format: number, money – in euros –, percent, days, minutes), date (ISO timestamp; grouping by day … hour in the sub-account’s time zone), boolean (SQL returns 1/0), tags (JSON array). lookup translates IDs into names (and order, e.g. pipeline stages); noGroup for free text.
  • Every source automatically gets the group Sub-account; sources with missing tables (requires) are hidden. A test that compiles all fields is in tests/reports.test.ts.
